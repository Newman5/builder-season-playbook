# Code of Conduct

This document consolidates participation, behavior, verification, and governance guidance found elsewhere in this repository for hackathon members to read in one place.


## Purpose

This event is intended to provide open, replicable safe spaces to learn, explore, and build meaningful products in public.

The format rewards consistent, verifiable participation rather than subjective judging or competition.

## Expected Conduct

Hackathon members should:

- act in ways that support a safe, open, builder-first environment
- keep participation visible, honest, and verifiable
- follow the published rules, dates, and clarifications
- use public channels and public evidence where the event requires them
- respect the official registration, repository, update, and verification processes

## Participation Principles

- Qualification is based on consistent, verifiable participation over time.
- There are no judges ranking entries; participants qualify by meeting public requirements.
- Public records matter: repositories, weekly updates, final presentations, and recorded feedback sessions are part of the event's verification model.
- The rules are meant to create clarity, not unnecessary bureaucracy.

## Builder Requirements

Participants in the Builder track are expected to follow these rules:

- Build a user-facing software product with clear user value.
- Include a clear payment gate.
- Work solo or as a team, but register every contributor.
- One person may only join one project.
- Maintain one official public repository per project.
- Keep that repository public until final payouts are complete.
- Start the official repository empty at the beginning of the event.
- Post at least one qualifying public weekly update each required week.
- Make the product publicly accessible by the end of the event.
- Deliver a complete final presentation with the required evidence.

## Disqualifying Conditions

The repo's existing rules identify the following as disqualifying or grounds for denied qualification:

- missing a required weekly update
- joining more than one project
- failing to provide verifiable public evidence
- missing, incomplete, or non-public required evidence
- using unnamed or anonymous contributors for a qualifying entry
- failing to keep the official repository public through final payout

## Feedback Track Conduct

Participants using the feedback track should:

- use the official Discord flow
- coordinate feedback in the official forum
- understand that builder teams may accept or refuse a volunteer before a session starts
- conduct feedback live
- record qualifying sessions
- keep shareable evidence for verification

## Admin Team Decisions

For this event, the following admin-governance standard should be treated as the operating rule:

- This repository is the source of truth for rules, dates, clarifications, and official decisions.
- Official clarifications published by admins in the repository or its issue tracker govern edge cases and interpretation questions.
- Admin verification determines whether the published qualification requirements have been satisfied before payout.
- Formal admin rulings on rule interpretation, evidence sufficiency, qualification, and verification are binding for the event.
- In practice, admin decisions on these matters should be treated as final unless the admins publish a revised clarification or ruling.

## How To Raise Questions

If a rule, edge case, or interpretation is unclear:

- open an issue in this repository
- use a clear title
- describe the question plainly
- link the relevant doc section when possible
- include a concrete example
- keep each issue focused on one question

Admins may use issues to publish official clarifications and formal rulings in the open.
